## Things to always do

- If you're not sure about something - ask first before doing any changes to the code
- Do not leave errors in any file
- Ensure any edited/created files are saved with LF line endings (no CRLF)
- After any larger change run, from the repo root, `pnpm lint <changed-file-1> <changed-file-2> ...` (oxlint), `pnpm format` (oxfmt, writes in place), `pnpm stylelint` when SCSS changed, and `pnpm knip` (unused files/exports/deps), and fix what they report.

## Where code goes

- `apps/*/src/components` - UI reused inside that app; `apps/*/src/containers` (app) and `apps/landing/src/app/<route>` (landing) - feature and route code
- `apps/app/src/common` - hooks and requests shared by more than one feature; `hooks`, `models`, `utils`, `router`, `store`, `i18n` for their respective concerns
- `packages/core/src` - anything both apps need. Core never imports from an app
- One component per folder as `index.tsx`, with its siblings (`styles.module.scss`, hooks, sub-components) next to it. Component name matches its file/folder name
- One component per file (`reactx/no-multi-comp` is an error). Prefer extracting repeated or complex JSX into a named component in a new file rather than a `renderXxx()` helper returning JSX
- Keep styles and small helpers local to the component; when the same helper or style appears in two or more files of the same feature, extract it to a shared sibling module (`common/`, `commonStyles`) and import it from there
- Inside an app, import through the root-relative alias (`components/...`, `containers/...`, `models/...`); across packages use `@locumo/core/*` and `@locumo/api/*`. Relative imports must not go deeper than `../../`
- oxfmt sorts imports - never reorder them by hand

## Component file layout

Enforced (and auto-fixable) by the local oxlint rule `locumo/component-file-layout` in every `.tsx`:

1. `'use client'` and other directives, then imports
2. `UPPER_SNAKE_CASE` constants and `lazy()` components may sit between imports and the component
3. the props type (`Props` or `<Component>Props`) directly above the component
4. the main component
5. everything else - helpers, maps, sub-types, secondary exported types
6. `export default Component;` as the last statement

Do not inline the default export (`export default () => ...`). Declare the component, export it at the end. Components and helpers are arrow function expressions (`func-style: expression`).

## Styling

- `import styles from './styles.module.scss'`, camelCase class names, combine with `joinClassNames` from `@locumo/core/theme/utils`
- `*.module.scss.d.ts` files are generated - never edit them by hand. They are regenerated by `pnpm --filter <app> generate:scss-types` and by the watcher inside `pnpm dev`
- Cascade layers are declared once in `packages/core/src/styles/globalStyles.scss`: `@layer mui, base, theme, core, components`. Put `packages/core` component styles in `@layer core`, app `components/` styles in `@layer components`, and leave container/route styles unlayered so they win
- Import shared SCSS by plain module path (Sass `loadPaths` points at `packages/core/src`): `@use 'components/layout/media' as media;`, `@use 'theme/colors/color' as color;`, `@use 'styles/primaryShadow' as primaryShadow;`
- Media queries: `media.greaterThan('mobile')`, `media.lessThan('medium')`, `media.between(...)` and their `container*` variants. In TS use `breakPoints` from `@locumo/core/components/layout/breakPoints` with `useWindowSize`
- Colors: never a literal hex. SCSS `color.get('primary')` / `color.get('grey', 0.1)`, TS `getColor('primary', alpha?)` from `@locumo/core/theme/colors/Color`. The palette is `baseColors` plus generated `50`-`900` variants
- Typography: no custom `font-size`, `line-height` or `font-weight`. Use `<Typography size="body">` / `<ResponsiveTypography>` from core, or the `typography.getSize('body')` / `typography.getFontWeight('bold')` mixins when the value must live in CSS
- For values that depend on props, pass CSS custom properties through inline `style` (see `packages/core/src/components/Button`) instead of generating classes
- `packages/core/src/theme/generated-vars.scss` is generated from the TS theme - after changing `baseColors`, `breakPoints`, `TypographySize`, `FontWeight` or `fontFamily`, run `pnpm --filter @locumo/core generate:scss-vars`

## UI components

- The design system is `@locumo/core/components` - `Button`, `inputs/*`, `Modal`, `typography/*`, `Divider`, `ListItem`, `icons/*`, `CategoryTag`, `Carousel`. Check there before writing a new component
- Use MUI only for behavior-heavy primitives core does not provide.
- Icons: `lucide-react` rendered through `IconBase`, or the SVG components in `core/components/icons`. Images and SVG files are imported as modules (`import phone from './phone.webp'`), never referenced by a hardcoded public path
- Feedback: `enqueueSnackbar` (notistack) for success and soft errors, modals for blocking errors

## i18n

- Every user-facing string goes through `t()` from `useSafeT` (`@locumo/core/hooks/useSafeT`). Never hardcode display text
- Key convention: `Module_Component_DescriptiveTag`, for example `Account_UserAddresses_NoData`. Short shared keys (`Email`, `Success`, `Accept`) exist for generic words - reuse them instead of adding a duplicate
- Translations live in `apps/app/src/i18n/resources/pl.json` and `apps/landing/public/locales/pl/common.json`; keys stay alphabetically sorted
- Values may contain HTML - it is parsed by the `parse` post-processor, so `t()` can return a node
- When a component takes a key instead of a string, name the prop `...Tag` (`titleTag`, `tooltipTag`)

## Data fetching

- Always load data with SWR through `useDefaultSWR` from `@locumo/core/hooks/useDefaultSWR`. Build the key from the API method name plus the params it varies on (`{ method: 'addressesSimpleRetrieve', addressId } as const`), or from the bare method name when there are none; return `Promise.resolve(...)` from the fetcher for the "nothing to fetch" case instead of branching outside it
- Call the backend through `useHttpClient`: `http.withMethod('userAddressesList').withDefaultErrorHandler().call(...)`, plus `withoutToken()`, `withPageErrorHandler()` and `withCustomErrorHandler()` where needed. The chain owns error handling - 401 opens the login modal, 400 goes to the handler, anything else opens the error modal. Do not wrap calls in ad-hoc `try`/`catch` with custom alerts
- `packages/api/src/Api.ts` is generated from the backend OpenAPI schema by `pnpm generateApi` - never edit it by hand
- Map API shapes into `models/` types at the fetch boundary (`toCamelCase`, `toLowerCase` for enums), so components work with domain models
- Keep a request with exactly one caller next to that caller; promote it to `common/` only when a second caller appears
- API dates stay ISO strings in models. Format them at render time with the prototype extensions (`value.toDate().toDateTimeString()`, also `toDateString`, `toTimeString`) or with `date-fns` plus `getLocaleForDates()`

## State (Redux Toolkit)

- Feature state lives in `containers/<Feature>/duck` - `slice.ts` (or `reducer.ts`) and `selectors/`, one selector per file named `selectX`, registered in `store/rootReducer.ts` and `store/AppState.ts`
- Read state with `useSafeSelector` when the value must exist; do not add guards for what it returns
- Modals are managed through Redux. **Do not** use `useState` to show/hide a modal:
  - `apps/app`: `dispatch(openModal('AddUserAddressModal', props))` from `containers/Modals/duck/reducer`, with the component registered in `containers/Modals/index.tsx`. Modal props are inferred from that component, so the call site is type-checked
  - `apps/landing`: its own `src/modals` with the same shape
  - Errors: `useOpenErrorModal` instead of dispatching by hand

```ts
dispatch(openModal('SimpleModal', { title: t('Title'), content: t('Text') }));
```

## Routing

- Paths are declared once in `@locumo/core/routing` (`app/appPaths`, `landing/landingPaths`) - no path string literals in components
- Navigate with `useAppNavigate()` / `useAppNavigateBack()` (app) or `useLandingNavigate` (landing); build hrefs with `getAppPath` / `getLandingPath`; link with `AppLink` rather than a bare `<Link to="/...">`
- Landing is an App Router app with `output: 'export'`: add `'use client'` only where a component really needs the client, and set page metadata through `generateMetadata` + `utils/pageMetadata`. Nothing may depend on per-request server APIs

## Forms (Formik + Zod)

- Always prefer **Formik** with **Zod**: define a Zod schema for the shape and messages, and validate from Formik with `validateZodForm` from `@locumo/core/utils/validateZodForm`
- Wire inputs with `handleChange`, `handleBlur` and `setFieldValue`; keep `name` aligned with the form state key
- **Field-level errors:** show the error state and helper text only when the field is **touched** and has an error - `error={!!formik.touched.field && !!formik.errors.field}` and `helperText={!!formik.touched.field && formik.errors.field}`
- Validation messages are translated, because they surface in the UI

## Effects

- Before writing **any** `useEffect`, validate it against [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect). If the logic can be expressed as a render-time calculation, an event handler, or a `key` reset, do that instead of an Effect
- Effects are only for synchronizing with external systems. Do not use them to transform data for rendering, handle user events, reset/adjust state on prop changes, or chain state updates

## Coding standards

- Prefer `undefined` over `null`
- Use only colors, typography and spacing coming from the design system
- Prefer promise chaining over `async`/`await`
- Avoid nesting code, it's better to return sooner to not nest code
- Avoid explicit types
- Avoid type assertions and casts where possible; prefer narrowing the source type or correcting the shared contract so future changes are checked by TypeScript
- Declare a union and its runtime value list once (`const xs = [...] as const;` plus `type X = (typeof xs)[number];`) and reuse it across schemas, state and API mapping
- Prefer bracket syntax (`T[]`) over `Array<T>` for array types
- Prefer default exports for a file's primary component, hook, helper or request function
- Do not export values or types until another file imports them
- Do not add empty lines between jsx elements
- Do not add `useMemo` or `useCallback` preemptively. Use them only when there is a measured or observed performance problem that they solve
- Extract magic numbers into named constants in `UPPER_SNAKE_CASE` (for example `ANIMATION_DURATION_MS`). This applies to JS/TS values, not to CSS declarations
- Use inline type imports (`import { type Foo } from '...'`) - oxlint fixes the rest
- Use Unix-style line endings (LF - `\n`) in all files. Never use Windows-style line endings (CRLF - `\r\n`)
